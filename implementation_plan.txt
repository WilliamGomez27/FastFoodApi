# Plan de Seguridad: FastFood API

## Diagnóstico Actual

Tras revisar todo el código del backend, se encontraron **5 vulnerabilidades reales** ordenadas por criticidad:

---

## 🔴 Vulnerabilidades Críticas

### VUL-1: Contraseñas con SHA-256 (CRÍTICO)
**Dónde:** [`auth.controller.js` línea 7](file:///c:/Users/gwill/OneDrive/Documents/CURSOS/Web/FastFoodApi/src/controllers/auth.controller.js#L7)

> [!CAUTION]
> **SHA-256 NO ES SEGURO para contraseñas.** Es un algoritmo de hashing de propósito general diseñado para ser *rápido*. Un atacante con una GPU moderna puede probar **10.000 millones de contraseñas por segundo** contra un hash SHA-256. Si alguien roba tu base de datos, todas las contraseñas caerán en minutos.

**Solución:** Reemplazar con **bcrypt**, que está diseñado para ser deliberadamente lento y tiene un factor de coste ajustable.

```diff
- return crypto.createHash('sha256').update(password).digest('hex');
+ return await bcrypt.hash(password, 12); // 12 = factor de coste
```

---

### VUL-2: Sin control de roles (CRÍTICO)
**Dónde:** [`server.js` - todas las rutas protegidas](file:///c:/Users/gwill/OneDrive/Documents/CURSOS/Web/FastFoodApi/src/server.js#L54)

> [!CAUTION]
> Cualquier usuario autenticado (incluso un `employee`) puede **eliminar productos, crear categorías y ver todos los datos**. Un empleado de caja no debería tener los mismos permisos que el administrador.

**Solución:** Agregar middleware `requireRole('admin')` que verifique el campo `role` del token JWT antes de permitir operaciones de escritura/eliminación.

---

### VUL-3: Sin Rate Limiting en el Login (CRÍTICO)
**Dónde:** [`server.js` línea 36](file:///c:/Users/gwill/OneDrive/Documents/CURSOS/Web/FastFoodApi/src/server.js#L36)

> [!CAUTION]
> El endpoint `/api/auth/login` no tiene límite de intentos. Un atacante puede intentar millones de combinaciones de contraseña automáticamente (**ataque de fuerza bruta**) sin ninguna restricción.

**Solución:** Agregar `express-rate-limit` que bloquee una IP después de 10 intentos fallidos en 15 minutos.

---

## 🟡 Vulnerabilidades Medias

### VUL-4: Dev Token público en producción (MEDIO)
**Dónde:** [`server.js` líneas 41-45](file:///c:/Users/gwill/OneDrive/Documents/CURSOS/Web/FastFoodApi/src/server.js#L41)

> [!WARNING]
> El endpoint `/api/auth/dev-token` genera un token de admin **sin credenciales**. Cualquier persona que conozca la URL puede obtener acceso total. Si este servidor llegara a un ambiente de producción, sería devastador.

**Solución:** Proteger el endpoint con una variable de entorno `NODE_ENV` y deshabilitar la ruta si `NODE_ENV=production`.

---

### VUL-5: Stack traces expuestos (MEDIO)
**Dónde:** Todos los controladores (ej: [`products.controller.js` línea 14](file:///c:/Users/gwill/OneDrive/Documents/CURSOS/Web/FastFoodApi/src/controllers/products.controller.js#L14))

> [!WARNING]
> En los bloques `catch`, se envía `error.message` directamente al cliente. Esto puede revelar información sensible del servidor (rutas de archivos, versiones de librerías, estructura de la base de datos) a un atacante.

**Solución:** Centralizador de errores que loguea internamente pero responde con mensajes genéricos al cliente.

---

## ✅ Lo que ya está bien protegido

- **SQL Injection:** ✅ Todos los queries usan `?` (prepared statements con `mysql2`). La inyección SQL está bloqueada correctamente.
- **Autenticación JWT:** ✅ El middleware `requireAuth` verifica la firma del token correctamente.
- **HTTPS Headers:** ✅ `helmet` agrega cabeceras de seguridad (CSP, XSS Protection, etc.).
- **Mensajes de error genéricos en login:** ✅ "Credenciales inválidas" no revela si el usuario existe o no.
